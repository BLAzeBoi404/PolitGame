# Проверки Sovereign 0.14

Сборка: .NET SDK 8.0.426, Release net472. Исполнение в этой среде: Debian 13, Mono, libgdiplus, Xvfb. GPU-путь проверяется настоящим OpenGL-контекстом **Mesa 25.0.7 llvmpipe**, который исполняет графику на CPU. Аппаратная видеокарта и Windows здесь недоступны.

## Корректность

- `tests-sdk.txt`: 603 успешных проверок; полный набор симуляции, сохранений, сценариев и воспроизводимости.
- `ui-results.txt`: обычный интерфейс и совместимый GDI-режим; все 515 проверок.
- `gpu-results.txt`: 23 проверки нового пути, включая сравнение framebuffer с CPU-картой, сохранение HUD и текстур при движении, масштабный слой войск, ввод через GL-контрол, выбор начальной страны, масштабирование, полный экран, смену размеров и восстановление рендерера.
- Задержанный тестовым барьером worker не мешает десяти презентациям камеры. Нажатия и сохранение ждут готового дня. Полностью сериализованный результат дня совпадает с синхронным движком. Закрытие во время расчёта корректно завершает его.
- `previous-release-save.txt`: сохранение с восемью днями России создано исходным exe 0.13, затем загружено 0.14 и продолжено ещё 30 дней.
- `legacy-save.txt`: исходное сохранение из пользовательского ZIP также продолжено на 30 дней без записи в исходный файл.
- `gpu-map.png`, `gpu-settings.png`: кадры из back buffer перед `SwapBuffers`, не макеты. `gpu-setup.png` показывает именно GL-слой атласа; нативные поля поиска/года находятся поверх него в отдельных WinForms-контролах и в этот framebuffer не входят.

Контрольные суммы exe, зависимостей и входных исходников — в `build-receipt.json`. Упаковщик сверяет их и требует успешные отчёты. Пользовательские `Saves`, настройки и временные тестовые XML в архив не входят. Изменений симуляционных формул или формата сохранения 12 в этой версии нет.

## Методика времени кадра

База — исходный exe 0.13 из коммита `9616b17f348699b28eb358ff8980219ef7bd5d76`, SHA-256 `c1a50cb763a4a2d840ce21a9dc5cf6c259992b66e4cf961d87c7b26a216dc155`. Обе версии запускаются одним сценарием `FramePacingProbe.cs`; для старой сборки он компилируется с `PROBE_STANDALONE` и использует reflection.

Окно 1600×900, высокое качество, средний масштаб 45, 3 765 соединений, два прохода по шесть секунд. События мыши идут от независимого таймера с целевыми 500 Гц, не более одного события в очереди. Отдельно считаются презентации и кадры, в которых изменилась камера. Фактически обработанное количество событий также сохраняется: программный GL влияет и на него.

Две последовательные пары старый/новый на паузе при лимите 60; одна пара с ускорением 7×; одна на паузе при лимите 165. Для ускоренного сценария диагностический ввод возвращается на карту после политического уведомления и возобновляет время, сохраняя само событие и его последствия. Автосохранение отключено только для замера, исходные настройки восстанавливаются. Прогоны не идут одновременно с тестами или сборкой. `LP_NUM_THREADS=2` задаёт число потоков программного драйвера в облачном контейнере с квотой четыре CPU, а не игровую настройку Windows.

Сохраняются все окончательные парные результаты, включая максимум, p95, количество интервалов >33/50 мс, загрузки текстур, растеризацию и перестройки HUD. Внутри GPU-кадра дополнительно измеряются подготовка команд и `SwapBuffers`.

## Практический вывод

Камера на готовом участке не перестраивает HUD и не отправляет готовые битмапы на GPU заново. Расчёт дня больше не выполняется в потоке окна при GPU-отрисовке. Это подтверждённые изменения архитектуры.

Облачный программный OpenGL не подтверждает устранение всех задержек: в нём остаются большие выбросы `SwapBuffers`, а некоторые интервалы и скорость обработки ввода хуже прежнего GDI. Их нельзя выдавать за аппаратную производительность. Числа ниже — интервалы доставки кадров на Xvfb, **не FPS пользовательского монитора** и не обещание 60–165 FPS. Рендерер всё ещё растеризует изменившиеся панели/большие выделения на CPU; следующий необходимый аппаратный замер — тот же сценарий с Windows-драйвером.

Мс: среднее / p95 / максимум. Для двух пар на паузе указаны медианы средних и p95, максимум — худший из двух; для остальных сценариев одна пара.

| Пауза, 165, повторный | 6.38 / 7.07 / 122.42 | 14.06 / 14.88 / 18.19 |

При лимите 165 повторный GPU-проход: подготовка команд максимум 2,84 мс, `SwapBuffers` максимум 17,32 мс. При ускоренной симуляции подготовка с обновлением UI доходила до 45,22 мс, `SwapBuffers` — до 179,32 мс. Поэтому аппаратный тест и дальнейшее сокращение работы при обновлении UI остаются необходимыми. Обе версии рассчитали дни в режиме 7×; точное число дней и автоматических возвратов с событий приведено в исходных отчётах.
